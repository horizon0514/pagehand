# 导出：杀手场景的一次押注

> 状态：**功能已建成，假设未验证** · 决定于 2026-08-07 · 本文写于 2026-08-12
>
> 相关：[`PLAN-subscription.md`](PLAN-subscription.md)（订阅与计费）

这份文档记录的是一次产品判断的**完整过程**，包括押注的理由、已经建成的东西、
第一次真实测试失败的细节，以及一个把整个定位重新框住的问题（与 RPA 的关系）。

结论写在前面：**导出目前不算已验证的杀手场景。** 它是一个成本可控、可回退的
押注，功能做完了，但决定它成败的那个数——真实站点上的首次成功率——一次都
没测过。

## 0. 已定的决策

下面各节写在这些决策之前；有冲突以本表为准。

| 问题 | 决策 |
| --- | --- |
| 护城河是什么 | **用户已登录的浏览器会话**。任何在公开页面就能做的事迟早被大模型自带的浏览能力吃掉 |
| 押哪个场景 | **导出**——给没有导出按钮的列表页装一个导出按钮 |
| 产品形态 | **不重做产品**。作为现有 agent 里被突出的一条路径，而不是单独的导出工具 |
| 目标用户 | 国内打工人（后台系统、内部 OA、招聘平台），不是海外 SaaS 用户 |
| 行数上限 | `MAX_FINDINGS` 200 → 2000。digest 只注入最新几条，所以这只约束存储和渲染，不约束 token |
| 竞争对照物 | **RPA（影刀等），不是 ChatGPT**。见 §5 |
| 尚未决定 | 走垂直还是走长尾。见 §6 |

## 1. 论点：护城河是登录态

Pagehand 唯一做得到、而 ChatGPT / Claude 联网 / Operator / Browser Use 做不到的，
是**它跑在用户自己已登录的浏览器里**。

推论：任何在公开页面上就能完成的事都不是护城河。「总结这个页面」是入场券，
不是付费理由。

只有你能做的事同时满足：

- 必须带登录态（后台、内网系统、招聘平台、订单页）
- 跨多个页面，人做要 30 分钟以上
- 反爬拦得住云端 agent，拦不住用户自己的浏览器
- 产出可验证、结构化

**重要修正（见 §5）**：这条护城河挡得住云端 AI，**挡不住桌面 RPA**——影刀一样
跑在你本机的真实浏览器里。写这条时没想清楚这一点。

## 2. 为什么押导出

> 给任何没有「导出」按钮的网页，装一个导出按钮。

几乎每个后台系统、每个平台的列表页都是「能看见、导不出、没 API、还得登录」。
今天的解法是手动复制粘贴，或者求开发写爬虫（要过登录态，很麻烦）。

选它还有一个理由：**它对上现有结构几乎是零改造**。`ledgerTools` 的 findings
结构（`key` 去重 + `data` 结构化字段）本来就是一张表，只是还没渲染成表。

`evidence` 字段解决了 LLM 抓取最大的信任问题：每一行都能点回原页面核对。

## 3. 已经建成的

分四层，全部在 `export-tables` 分支上（4 个提交）。

### 3.1 抽取引擎

`src/lib/tools/tableScripts.ts`（页内脚本，零依赖）+ `tableTools.ts`（两个工具）

- `infer_row_schema`：探测重复结构 → **一次** LLM 调用推断
  `{rowSelector, fields, keyField, nextPage}` → 立刻试抽验证
- `extract_rows`：拿 schema 在扩展侧循环翻页，每页纯 DOM 抽取，**零 token**

三个关键设计：

1. **行数据不进上下文。** 直接写 ledger，只回 `{rowsAdded, pagesVisited, columns, stopReason}`。
   值得导出的列表恰恰是不值得念出来的列表
2. **翻页循环在扩展侧**，不在页内——页内循环遇到真实导航会被打死
3. **findings 不带 evidence/rationale。** digest 每步注入最新 15 条，一百行引文的
   成本会超过抽取本身省下的

### 3.2 结果与导出

`src/sidepanel/lib/findingsTable.ts` + `exportActions.ts` + `LedgerPanel.tsx` + `ResultBar.tsx`

- 表格形状**推断**而非固定：key 出现在自己 data 值里的是抽取结果，给它自己的列；
  否则保留 Key/Summary/Evidence
- CSV 带 UTF-8 BOM + CRLF（没有 BOM，中文在 Excel/WPS 全是乱码）
- TSV 走剪贴板，粘进飞书表格一列一格——**日常比下载文件用得多**

### 3.3 入口

`ExportChip.tsx` + `detectList.ts` + `ChatThread.tsx` 的建议项

关键约束：探测**只用 `permissions.contains()`，从不 `request()`**。每次切标签页
弹授权框比不知道更糟；也绝不用 `chrome.debugger` 探测，那会为一个没人问的问题
弹出 Chrome 的调试横幅。探测不到就照常显示 chip——**猜错代价是一行界面，
藏错代价是整个功能**。

### 3.4 保存与重跑

`src/lib/tasks/exportTasks.ts` + `useExportTasks.ts` + `ExportTaskList.tsx`

第一次跑付一次模型调用，之后每次都不付，因为 schema 就在那儿。
用户回来不是为了同一张表，是为了「这周多了什么」，所以 `lastKeys` 一并存下。

**只有采集到行的运行才允许覆盖基线**——否则登录态过期这类失败会清空 lastKeys，
下次成功运行把整张表报成"全是新增"，正好毁掉这个功能唯一的价值。

## 4. 唯一一次真实测试：失败

2026-08-07，在 Gmail 上试，四层同时崩：

1. `infer_row_schema` 返回空字符串 → 抛异常
2. 模型改用 `evaluate_script` 手抓 → 9 行数据进了**对话上下文**，`extract_rows`
   从未被调用
3. 模型把整个结果集塞进**一条 finding 的 `data`**（`{columns:[], rows:[]}`）
4. ledger 空 → 面板不渲染 → 用户看到「I got 9 rows」，屏幕上什么都没有；
   后来能渲染了，导出的 CSV 是一行两个 JSON 块

四层都已加固（工具不再硬失败、渲染层能摊开乱塞的数据、结果入口出现在视线里），
但**加固的是韧性，不是效果**。「不会崩」和「杀手级」之间差得很远。

还有一个没修的问题：Gmail 那个会话页上，9 封邮件确实是那页唯一的列表——
模型**没选错**，但这个结果对用户没用。工具没有「这个列表值不值得导」的概念。

### 验收线还没跑

当初定的 MVP 验收线是「**10 个真实站点里 8 个一次跑对**」。

这个数一次都没测过。跑通的是两个自己写的 fixture（`e2e/fixtures/list.html`、
`lists.html`），和一次失败的真实页面。

## 5. 与 RPA 的关系（最重要的一节）

对照物不是 ChatGPT，是**影刀这类桌面 RPA**。这个认识来得太晚，它改变了定位。

### 正面比会输

影刀能做的：可视化流程、元素拾取、录制回放、桌面应用自动化、Excel 操作、
**定时无人值守**、异常重试、分支判断、应用市场里现成的电商/财务流程。

我们功能上是它的子集，且有硬伤：

- **不能定时、不能无人值守**——侧栏关了就停
- 没有错误处理、重试、分支
- **可靠性反而更差**——RPA 录下来的选择器是确定的，LLM 推断不是
- 它在电商、财务有现成模板，正压在我们想去的地方

### 真正的差别只有一条

**RPA 要你先搭一个流程，我们不用。**

| | RPA | Pagehand |
| --- | --- | --- |
| 固定成本 | 高（拾取元素、定义循环、处理翻页、调试） | ~0 |
| 边际成本 | ~0 | 一次模型调用 |
| 划算的场景 | 同一流程跑 1000 次 | 跑 1~5 次 |

RPA 的经济学**要求任务足够重复**。不值得搭流程的活——一次性的、临时的、
每个网站都不一样的——是 RPA 结构性覆盖不到的地方。

第二条差别是**形态**：影刀是「打开一个工具去做一件事」，我们是「在你正在做的
事情旁边」。这条比零配置更耐久，因为零配置可以被追平（影刀、UiPath 都在加
LLM 元素识别），形态不行。

### 不能吹的几条

- **登录态**：对云端 agent 成立，**对 RPA 不成立**——桌面 RPA 一样跑在本机浏览器
- **反爬**：同上
- **零配置的领先窗口有限**：这正是 RPA 厂商在冲的方向，而他们有引擎和渠道打底

## 6. 岔路：垂直 vs 长尾（未决）

§5 暴露了一个之前没讲清的矛盾：**垂直 + 高频 + 重复 = 正好是 RPA 的主场。**

| | 走垂直（如招聘） | 走长尾 |
| --- | --- | --- |
| 收钱 | 容易，猎头/HR 有预算 | 难，一次性用户不订阅 |
| 对手 | RPA + 垂直工具，正面打 | RPA 覆盖不到 |
| 取胜靠 | 功能深度（详情页下钻、反封控） | 零门槛 + 存任务转周期 |

**倾向长尾**，但把「保存任务 + 重跑 diff」当主线而不是附加功能：
用户因为一次性需求进来（零门槛），用完发现「下周还要再看一次」，于是存成任务。
**入口是长尾，留存是重复。**

如果这条成立，对外文案该讲的不是「AI 版 RPA」，而是「**不用搭流程**」——
把对比对象明确设成 RPA，差异点钉死在固定成本上。

### 招聘场景的单独评估

技术契合最好（DOM 规整、反爬最凶、平台**永远不会**给导出按钮——那是它的商业
模式而非疏忽、重跑 diff 天生契合 sourcing、已经在付费）。

但三个前置问题：

1. **候选人数据是个人信息**——涉及个保法，基本必然违反平台协议。这条决定了
   能做多大声、能不能公开卖，需要真的去查
2. **用户的账号是他的饭碗**——现在翻页间隔 1.2s 连翻 10 页，真人不会这么快。
   节奏可配置 + 随机抖动是**入场条件**，不是优化
3. **列表页没有你要的东西**——真正值钱的在详情页。也就是说招聘场景下
   「详情页下钻」不是可选项，是全部价值，而它一直被标为 Step 4 没做

## 7. 还没有答案的问题

1. **首次成功率是多少？** 决定生死，半天可测，一直没测
2. **翻页会不会触发限流？** 招聘方向上如果撞墙，后面都不用谈
3. **常驻 chip 的点击率？** 入口就是为了可测量才做的，但**没有任何埋点**——
   「让数据决定」这个论证目前是没有数据支撑的
4. **用影刀的人有多少活是想自动化但懒得搭流程的？** 这个池子的大小决定长尾
   路线宽窄

## 8. 下一步（按顺序）

1. **跑 benchmark**：8–10 个真实工作页面，记录首次成功率 / 是否限流 / 列对不对。
   半天。3/10 说明场景选错，7/10 说明打磨就能到 9
2. **列可编辑**（重命名、删列）：比把推断做到完美便宜一个数量级，把「列选错了」
   从死局变成五秒钟的修正。也顺带救了兜底路径的 `列1 列2` 体验
3. **翻页节奏可配置 + 随机抖动**：不管最后选哪个场景都不亏
4. **最小埋点**：否则问题 3 永远没答案

## 9. 记录：判断错的地方

留着，因为这些是看代码看不出来的。

- **一开始建议把整个产品砍成单一用途的导出工具。** owner 否掉了，是对的——
  那是没验证就把已上架的产品全押上去。改成现有产品里的一条路径后，成本和
  可回退性都好得多
- **护城河讲成「登录态」时没考虑 RPA。** 对云端 AI 成立，对桌面 RPA 不成立。
  正确的对照物应该从一开始就是影刀
- **第一次真实测试就翻车。** 推荐讲得很笃定，Gmail 上四层同时崩
- **建议「选招聘深挖垂直」时，没意识到那正好是 RPA 主场。** §6 才把这个矛盾
  摆出来
- **下载按钮改了三次才被看见**（默认折叠 → 纯图标 → 位置在视线之外）。
  一个功能要改三次才能被发现，通常说明整条流程本身不够自明，不只是按钮小
